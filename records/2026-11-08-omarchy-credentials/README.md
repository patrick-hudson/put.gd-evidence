## Why earlier reports differ

Worker D explicitly used a disposable lab keychain. The earlier scripted nightly pass called `prepare_live_keyring`, starting a private daemon; those successful live uploads did not establish the stock user's path. Clipboard #1317's final published records prove its loopback clipboard tests, not live Omarchy credential acceptance. Its failed import exception is absent from the retained final results/logs, so a unique historical root cause cannot be asserted.

A distinct import problem was reproduced without any credentials: the Fedora-built lab bridge cannot start on a stock AppImage-only guest (`libqt6keychain.so.1` missing, loader exit127). The AppImage itself supplies its own runtime and works. Loading that one bundled library for the test bridge, or installing the native package's normal `qtkeychain-qt6` dependency, makes the bridge usable. This is a harness runtime distinction, not evidence of a product credential failure. The empty retained `live/ckoi` metadata directory also prevents assuming that the historical attempt reached the bridge import stage.

A real helper bug found here is fixed in [PR1323](https://github.com/patrick-hudson/put.gd-desktop/pull/1323), head `a4f14240112221bc33619e296c0c33b341c45d2b`: the Proton collector previously waited for every `^putgd` process, including the clipboard keeper, after the resident quit. It now waits for the exact resident. All32 tests pass on f44, including real process-name fixtures restricted to a fixture PID. Native lending then completed successfully with the keeper present. Final CI passes; zero unresolved threads; review bodies read, including outside-diff findings (none). The old review's docstring finding was fixed in the final commit. More than seven minutes elapsed after the last push. No product change was needed; PR remains unmerged.
